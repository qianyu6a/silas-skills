### Word-for-word quote verification (mandatory)

A per-block receipt only proves "these blocks were visited", not "the quotes were copied correctly". Sub-agents typing excerpts by hand make three high-frequency errors: missing characters, dropped words, replaced punctuation (curly quotes turned into straight quotes, em dashes turned into hyphens). Receipts cannot catch them; the check must be programmatic.

At every step's wrap-up, run a word-for-word check over the candidates: take each "source excerpt" back into the block file's **raw bytes** and do a substring comparison; list the misses and have the sub-agent correct them against the source and re-verify; anything that cannot be fixed gets a note in `state.md`. The check script follows each workspace's `work/verify_quotes.py`. **Empty excerpts must be counted separately** — the empty string is a substring of any text, so substring comparison lets it through; add a line counting "empty excerpt" to the check script, and if the count is not 0, backfill a single-line complete sentence from the block file.

**A literal hit and block-number attribution are two separate things — reconcile them separately.** Substring comparison only proves "this sentence is in this material" — the script passes on a hit in any block, so a wrong block number (content from block 12 labeled block 13) sails through the whole batch. In repeated spot checks, block numbers, not excerpts, were the most frequent error. Add a block-number consistency check at wrap-up: parse each item's "source location" block number, then find which blocks the excerpt actually hits in, and list corrections for the mismatches; when dispatching tasks, write "block attribution must be checked item by item with a script" into the requirements.

**When a section body and its excerpt fall in two different blocks, attribute by the excerpt's source.** For example, a section's discussion paragraph was cut into the next block: the location field gets the block number of the excerpt's source block, with a parenthetical noting the body block ("discussion paragraph in block N"), and receipt counts also follow the excerpt's source block — verifier and receipts then use the same convention and cannot disagree. The verifier side must correspondingly allow the location field to declare multiple block numbers (including range notation such as "blocks 12-13" — expand the range and try each block, pass on any hit); do not hard-match only the first block number.

**When fixing a sub-agent's output, read the actual file from disk before writing replacement conditions.** The format quoted in a report (e.g. "block 13" with a space) and the actual format in the file (e.g. "block13" without one) often disagree, and replacement rules written from the report then silently match zero times; immediately after replacing, re-check how many places changed and whether the annotation distribution reconciles with the receipt section.

**Using the patch tool on script lines containing escape sequences easily corrupts the file.** Literal sequences like `\r\n` get parsed into real control characters by the write layer (result: unterminated strings, syntax errors). Fix such files with a python script instead: build the needed backslashes and newlines with `chr(92)` / `chr(10)` concatenation, or first normalize `\r\n→\n` and then do line-level replacement; re-run the script immediately after editing to verify — do not confirm by eye.

**Scripts that append and write back must not assert "the file must be pure CRLF/LF".** After several batches of appends the file's newlines are often mixed (each batch wrote back differently) and the assertion is guaranteed to fail. Read with `.replace('\r\n','\n')` normalization and write back as LF only (write back with `open(p,'w',encoding='utf-8',newline='')` — Windows text mode converts newlines to CRLF, so one append rewrites the whole file's line endings); treat "unified newlines" as a processing premise, not as a file fact.

**Trap: read_file is not byte-faithful.** It normalizes whitespace, blank lines and some punctuation — a sub-agent copying quotes from what read_file displays will fail on whitespace differences invisible to the eye. Quote extraction and repair always go by the block file's raw bytes; the most robust approach is a script that slices the quote string out of the block file by start/end anchors and writes it into the candidate directly, never passing through manual typing.

**Two traps in cutting quotes by anchor.** ① read_file's displayed line numbers shift with re-wrapping and cannot be used as source line numbers; PDF extraction also splits a character at the end of a line onto the start of the next (anchor written "date minus", actual source is "da" + newline + "te minus"). Precise quoting can only be done by a script matching the anchor on the in-memory string with "identical after removing all whitespace" — do not use line numbers, and do not substring-match a bare anchor directly; ② block files often carry CRLF: after reading, first `.replace('\r\n','\n')` before comparing (line numbers unchanged); a mis-joined newline makes the whole batch miss. Always prefer physical whole lines as anchors (a whole line never splits mid-line); when a phrase must be truncated, avoid wrap boundaries.

**Excerpts must not contain `[page N]` page markers.** In-block page markers are their own line, but a sentence spanning a page break has one wedged into the middle of it ("… .[p.158]next sentence…"); any excerpt containing `[p.` is rejected outright — when selecting sentences, avoid page-spanning paragraphs and take only adjacent non-spanning clauses. In build scripts, assert "exists verbatim" and "contains no `[p.`" together as a double assert (one workspace had an entire batch sent back over this).

**In python scripts that build candidates, text containing single quotes (e.g. 'OPEN', 'Dave') must be double-quoted on the outside.** An unescaped single quote hard-coded into a script is the most frequent script-level failure; syntax-check a script before running it (e.g. parse the source once with ast).

**If the check script reports a total wipeout, suspect the script itself first.** When a regex carries both a `^` line-start anchor and a cross-line `.*?`, the flags must be `re.S | re.M` — with only `re.S`, `^` matches only the start of the whole string and every item is falsely reported "field missing". Locate such problems with `repr()` and character-by-character hex dumps of the suspect region; do not stare at the source and guess. For the five-track wrap-up, use the parameterized version shipped with this skill, `scripts/verify_candidates.py <workspace>`, instead of having every track's sub-agent produce its own — the self-produced ones have had three classes of problems: flags, anchors, matching conventions. It has several error-prone conventions built in: **three-level fallback excerpt extraction** (code fence → `> ` quote block → same line with outer CJK quotation marks stripped) — the five tracks' on-disk formats are not necessarily uniform, and hard-wiring a single format falsely reports "missing field" for a whole case/glossary track; **multiple location-field spellings** ("block N" in both of the source's single-block spellings, and "blocks N-M", are accepted — comma-joined "blocks N, M" is **not** accepted; multiple blocks must always be written as a range "blocks N-M"); **empty excerpt judged failed** (miss this and the whole track is falsely all-green — the empty string is a substring of any text); **second chance for cross-page noise lines** (after a strict match fails, retry after stripping header noise lines line by line — cross-page excerpts are kept as-is and not falsely reported, while full-width/half-width differences are still corrected as real differences; the strip list has only three kinds: page-marker lines / pure-number page-number lines / `N.M` subsection-style lines — irregular headers (e.g. "Chinese numeral + title" lines) are not on it: when you hit one, pick a contiguous clause that does not cross it, **do not expand the strip list**, expanding it damages body text). Comparison always **normalizes both sides the same way** — normalizing only the source side errs in both directions: short anchors with no whitespace "falsely pass", anchors crossing a wrap "falsely fail", and both have caused batch-level misjudgments. **The verifier is designed for "whole batch, all runs"** (from batch 2 on, the file holds multiple batches' content): reconcile the receipt section by concatenating segments (`'\n'.join(text.split('## Per-block receipt')[1:])`, do not take only the last segment); use `(\d+)` rather than `(\d)` for block numbers — multi-digit block numbers (e.g. "block 10") are silently missed by a single-digit regex; the location field may contain multiple block numbers; line-level checks use substring (`any(exs in ln for ln in lines)`) rather than whole-line equality — excerpts are often in-line fragments, and whole-line equality fails correct ones.
