# Step 5 Construction · Preparation and Dispatch Recipe

When several hundred verified primary entries must be merged into 6–10 skills and each skill gets one sub-agent constructing it in parallel, follow this recipe. The construction standards (merge principles, count caps, template hard requirements) live in step 5 of SKILL.md and `references/skill-template.md`; this file covers only how to operate.

## 1. Merge grouping (script, lead does this)

1. Take the final kept set from `work/summary.json` (kept + not merged; the content of merged entries is already folded into the framework entry and is not listed separately). **Workspaces that went through a resift are the exception**: generate the kept set from the resift's "surviving units" (the resift maintain set) instead of the first round's keep list — the latter errs in both directions: it drops "absorbing trunks" (F entries whose verdict column says "merge" but whose note says "this one is authoritative" — their content must be retained) and mixes in soft duplicates that were already absorbed. For how to identify them and merge them back, see section 6 of `verification-prep.md`.
2. **Automatic rough split by chapter**: parse the "Chapter X" out of each entry's "source location"; when only block numbers are present, fall back to the "chapter start block table" — scan the first few lines of every block file for a chapter title to get "start block → chapter", then forward-fill across every block. Field-tested grouping reference (about 10 groups): data processing and text / iteration and generators / file IO and encoding / functions and decorators / classes and metaprogramming / modules and imports / networking and IPC / concurrency / script debugging and performance / C extensions and cross-language.
3. **Hand-correct the boundaries**: automatic grouping follows chapters, but "the user needs these in the same situation" is the real grouping criterion — move misplaced topics to another group (example: a decorators subsection landed in chapter 9 and belongs in "functions and decorators", not "classes and metaprogramming"). After correction no group is left with nothing to do.
4. Write each group to `work/groups/<group>.md` (full entry text, same format as the verification task pack).

## 2. Material slicing (script)

- Case material: split `cand/case.md` on `### Block N` sections and group by block number → `work/groups/cases_<group>.md`; when the file has no section headings (entries are flat and the block number appears only in the `- Source location: Block N` field), switch to parsing the block number out of the location field — the lead first draws a "block → primary group" mapping table (one block goes to exactly one primary group; do not scatter the same block across several groups; groups short of material do not pad their numbers, the primary entries govern).
- Counterexample material: every entry in `cand/counterexample.md` carries a `- Source location: Block N` field; group by that block number → `work/groups/counter_<group>.md`.
- Entry heading formats differ from candidate file to candidate file (framework `## N. `, principle `## Principle: `, case `## Case: `, counterexample `## Counterexample NNN: `) — write a parser regex for each file; do not expect one regex to cover four files.

## 3. Dispatch the constructors (parallel, one sub-agent per skill)

Task description essentials:

- Role: skill pack constructor; background: book title, primary entries have passed triple verification, topics this group covers.
- Give all five inputs by path: ① this group's primary entries `groups/<group>.md`; ② case material (note the file is large, ~40–90KB — locate with grep, no need to read it all); ③ counterexample material (same); ④ `skeleton.md` (must read the "Blind spots and boundaries" section — the only source for "when not to use it"); ⑤ `references/skill-template.md` (must read in full).
- Copy the format hard requirements into the task verbatim: first line `---`; write only name and description; description 60–120 characters by total character count (write the scenario sentence first, then count); six-section structure; "How to do it" 5–12 executable actions; self-check "cover the source and reread — if it reads like a chapter summary, rewrite it".
- Budget about 10–15 tool calls to get it right in one pass (read template/skeleton → read primary entries → grep the material → write to disk → probe self-check); put scratch scripts in `work/` with a group-name prefix (one batch shares `work/`; identical names collide).
- Write to disk in one go, or read it all first and then overwrite — the host has overwrite protection, so appending to the same file in batches is refused.
- Besides `skill-template.md`, also give the path of **one finished SKILL.md of the same kind** (a pack from a previous book with the same structure; for later waves of the same book, use the first finished pack from this book) — copying a live structure is more concrete than an abstract template, and it keeps style more consistent across packs.
- Estimate material size in **characters** (python `len()`), not `wc -c` bytes: in Chinese text the byte count is roughly 2–3× the character count (group material displayed as 183KB in bytes is about 76K characters, which a sub-agent can read in one pass) — "only use python chunked reads above 60K characters"; do not split files because the byte figure looks inflated.
- Write the quality requirement into the task and recommend a self-check: every kept entry must be absorbed by at least "How to do it" or "Judgement criteria" (same-kind entries may be merged), and nothing may be invented; before delivery, self-check with **keyword probes** (pick one distinctive word per kept entry and check that it appears in the body) — constructors will then proactively patch a few missed absorptions. If a probe reports a miss, first re-check for a false positive: probe wording that differs from the body wording triggers a false alarm; "rewritten rather than dropped" = absorbed successfully.
- **Cross-reference budget for description**: 60–120 characters cannot hold every sibling skill name (seven full names alone are 100+ characters) — cross-reference only the nearest 2–3 (short suffixes such as `state`/`emotion` are fine), and put all sibling names in the body's "When to use it"; count before writing the body, because coming back to squeeze them in after the body is written will inevitably exceed the limit. Trigger words are always the user's colloquial phrasing; in-book terms ("soft zone", "drawing a small circle") may appear only in the body, never as trigger words.
- **Copy probe words verbatim from the source**: one function word off in a quotation causes a miss ("never once" vs "never") — copy probe words straight from the characters of the source excerpt; when two primary entries share one distinctive word, validate with a two-word combination to prevent false positives.

## 4. Wrap-up (lead does this)

- After everything has returned, run the **metadata gate script** and re-verify item by item: first line `---` / name = folder name / lowercase hyphens / description 60–120 total characters by `len()` / no extra fields / `skills/` root holds only skill folders. **Do not trust sub-agent self-reports** — they write their own validation script and report PASS; run the independent re-verification anyway.
- **When a group label disagrees with the material content, the material wins.** Planned groups are often written from an expected chapter mapping, and the actual block content can be offset wholesale from the label (example: three constructors simultaneously reported "label does not match content", off by one). Handle it: ① constructors write to the material's actual content — do not force the wrong label, and do not fetch extra material to satisfy a label; ② the lead renames the finished skill to match the actual content — `mv` the folder and change the `name:` field in SKILL.md (**both places**, then grep to re-verify), and record the rename and the reason in `state.md` and the final `checklist.md`; ③ a constructor proactively reporting a mismatch is a valid signal, not a failure.
- **Before the blind test, cross-scan the sibling skills' description trigger words.** When two skills both claim the same trigger concept (e.g. "variable naming" appearing in two packs), the blind test will most likely judge it "boundary" — acceptable (triggering either one helps), but predict it; to make it cleaner, keep the closer one and give the other a differentiated trigger word — **make that change before the blind test**; do not touch descriptions after it.
- Spot-check 1–2 SKILL.md bodies (cover the source and reread), rework any that fail quality; only when all pass, go on to the step 6 blind test.
- Reference implementation: preprocessing `prepare_verify.py`, pack splitting `generate_parts.py`, summarizing `summarize_verify.py` in `D:\distill_cookbook\work\` (the grouping script can simply be written fresh per this recipe).
