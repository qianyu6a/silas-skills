# Large-Book Batch Extraction Playbook (8 batches × 5 tracks, field edition)

> Source: October 2026, a live run on *Python Cookbook* — 40 blocks / 8 batches / 30+ sub-agents (1000+ candidates, all passing the word-for-word check). Applies to: books with more than 20 blocks that need multi-batch parallel extraction by sub-agents.

## Architecture

- 40 blocks → 8 batches (5 blocks each) × 5 tracks (framework/principle/case/counterexample/glossary term).
- Dispatch 5 sub-agents in parallel per batch with one delegate_task (cap 6, leaving 1 for the main thread); **batches are serial** (the next batch reads the file after the previous batch's appends).
- The nine elements of every sub-agent instruction: extractor path / this batch's block list / no skipping within a block / output file (append mode) / per-block receipt / format follows the extractor / temp script prefix (bN) + work directory / paths containing Chinese used verbatim / tool budget.
- **Re-dispatching a single track while the next batch writes the same file must be serial**: when redoing one track of batch N, the same track's sub-agent in the next batch must not be started concurrently — two sub-agents writing the same candidate file always conflict (one hits the overwrite guard and refuses to write, or they overwrite each other). Finish the redo track first, then dispatch the missing track of the next batch; spend the parallel budget on batches that write different files.

## One-shot sub-agent workflow (budget: 15 tool calls)

1. Read the extractor definition (references/extractor-*.md);
2. Read all 5 blocks into memory with a single python `read()` call and print an overview (block name + character count + first line is enough, **do not print whole blocks** — 5 blocks of full text will hit the single-output cap and force several extra read rounds) — **do not use read_file pagination** (for a book with large blocks, reading 5 blocks page by page takes 11+ calls, and the budget is burned out at the "read" step). This must be spelled out in every sub-agent's task description: sub-agents cannot see this playbook, so writing it only here is useless;
3. Build the candidate data table and **land it as a work/ build script first** (data + word-for-word assertion + write to disk + read-back re-check in one piece, **by default run it straight through: write to disk automatically once the check passes**): before writing an excerpt, assert that it "exists word-for-word in the corresponding block". Three write-to-disk disciplines: ① "dry-run the check first, then write to disk in a separate call" is forbidden — in measured multi-track runs the check finished but the write never happened before the cap hit, forcing a full redo of the batch; leave check-only mode to the lead for debugging. ② Writing to disk beats a perfect build: better slightly fewer entries in the store soon than everything stuck in context; for batches of very large blocks (5 blocks totaling >80k characters) build block by block and write incrementally every 2-3 blocks — half a batch stored and pending completion beats the whole batch waiting in context for one final write. ③ When the data is already in a file, the worst case at the cap is "script ready but not finished", and the lead closes it out with one command;
4. Render and write (insert candidates before the receipt section; append this batch's 5 receipt lines);
5. Re-parse the file and verify the entry counts.

Triage a capped sub-agent by its artifacts: ① script/data ready → the lead runs it through directly and fills the gaps (first run the script's check mode to re-verify anchors, then fix the one or two entries that still fail according to the locations it printed, then write); ② no script and no data → **re-dispatch only that track** (do not redo the whole batch), and attach the previous round's findings (block→chapter mapping, the anchor fix table already located) to the new task description so the new sub-agent does not start from zero.

Measured: a sub-agent that does not follow "one-shot" hits the cap at 85-95% of its budget and needs manual wrap-up by the lead (20-40% of the time). From batch 2 on, putting this workflow and the previous batch's pitfalls into the context made the line noticeably more stable (batch 5 had zero rework).

**Up-front hard checks against rework (the main lever for cutting the cap rate; write each into every batch's task description)**: repeated fix round-trips are the number one cause of hitting the cap — front-load these items as hard checks and do them once: ① excerpt completion only within **the same paragraph**, scan to the nearest `。！？`, never across `\n\n`; ② after writing, scan for **doubled-prefix sticking** (e.g. `## Case: ## Case:` — when the template repeats the prefix, entry counts look normal and it is missed unless checked by eye) and **zero-width characters** (`\u200b\u200c\u200d\ufeff`, invisible, assertions do not catch them); ③ blank-line separation between entries consistent with the existing file; ④ idempotency assertion before writing (the new entry title is not already in the file); ⑤ merge "read the existing file + read the blocks + build + assert + write to disk + read back" into **one** script run in one shot.

## Block files and excerpt discipline (most important)

- Block files are CRLF: `.replace('\r\n','\n')` on read.
- The line numbers read_file shows get rearranged by soft wrapping and **must not** be used as source line numbers; to locate source text, write python and use find/slicing on strings.
- Prefer whole lines (physical lines) as excerpt anchors, avoiding phrases that cross a soft wrap (the wrap splits characters and breaks the anchor, e.g. "date / but rather" split apart). **When a paragraph inside a block is a very long single line (measured at 150–1200 characters per line, where "whole line" no longer works), switch to "the sentence window around the anchor"**: cut full sentences at `。！？\n`, extend one sentence forward if under 45 characters, back off to the sentence end if over 230 characters — the excerpt lands inside sentence boundaries and does not copy a whole paragraph.
- **OCR line breaks push spaces into the middle of words/sentences** ("this is  entirely a kind of reverse thinking", "but he did not  notice"): always take "the shortest unique fragment without spaces" as the anchor and locate it with the normalized mapping of the standard locating method below; a direct `find` on a string containing spaces always misses — the text is not broken, a line-break space got mixed in; handle it as normal and do not fix the source.
- **Excerpts must not contain `[page N]` page markers**: when a sentence crosses a page the marker lands mid-sentence — take the adjacent clause that does not cross the page; assert twice before writing (exists word-for-word + does not contain `[page `).
- In Python scripts, wrap text containing single quotes in double quotes (a repeated crash point).
- English soft wraps may be missing a space; when necessary, use the "insert a space at the wrap" variant to locate.
- **The most frequent cause of anchor mismatch is "one character off from the source"**: synonymous rewording ("if" written as "provided that"), dropped words ("described" written as "describe", "worked hard to persuade" copied as "persuade"), word order ("in a certain order" written as "in order") — the fix is to retry with a shorter unique substring, not to keep trying long sentences; perfectionism about "only pass when the whole long sentence matches" burns the budget.

- **Produce excerpts by default with "locate the anchor → slice from the source", never hand-copy**: hand-copying long excerpts reaches a batch-level error rate of up to 30% (one measured batch had 47 wrong out of 151), and every error was an invisible-to-the-eye difference (one character off, a dropped word, a full-width "－" copied as a half-width "-"). **Standard locating method (the preferred production path; also use it to batch-rescue excerpts already written wrong)**: write a norm2raw — walk the block text character by character, skip `[page N]` and whitespace, and record the mapping "normalized character → source index"; once `norm(anchor)` hits in the normalized stream, use the mapping to look up the **real source fragment** and backfill it (word-for-word by construction, and it holds across soft wraps too). Shorten the anchor progressively and retry (whole sentence → first 24/20/16/13/10/8 characters), and leave only the few that truly cannot be located to manual work — do not let a single-digit number of failing entries block the whole batch's write. **PRE-CHECK every anchor in one pass on the first round, report all failures at once, then fix** (trial-and-error one entry at a time is the main way to burn budget); put this method in the sub-agent task description — sub-agents will not invent it themselves, and in measured dispatches all five tracks had zero mismatches on the first round.

- **When the check fails, change the excerpt by default, not the checking standard**: normalization tolerates only whitespace, line breaks and `[page N]`; full/half-width punctuation and glyph differences ("12－60" vs "12-60", "if" vs "provided that") count as real differences — the fix is to align the excerpt with the source, not to loosen the checker (loosening delivers a whole batch "looking all green" with wrong characters). The only exception channel: **header noise lines on cross-page excerpts** — the excerpt itself is clean (no `[page `), the content is real, but at the page boundary the source inserts a header line (a page-number line, an `N.M section name` style header line), so strict matching must fail; the full validator gives these a second chance (strip "page marker lines / pure 1-3 digit page-number lines / line-initial `N.M` section-style header lines" per line, then retry — already built into `scripts/verify_candidates.py`), and such excerpts are kept as-is without rewriting. **But the excerpt must be a contiguous substring of the source**: when a header/page marker sits mid-sentence, pick a different contiguous clause that does not cross the insertion (shorter is fine) — **do not cut out the noise and splice**; a splice hits under no standard and the second chance cannot save it either (the second chance only restores genuine cross-page cases where the text is contiguous once noise is stripped per line; it does not handle manual splicing).
- Books with an OCR-derived text layer often have **vertical ghosting** (the same sentence repeated across 3-4 physical lines): always take **a single line or a single-line prefix** as the excerpt (a prefix = a contiguous fragment from the start of the line to any position within it; ending mid-sentence is fine as long as it is word-for-word) — **cross-line excerpts always fail in ghosted blocks**: the repeated lines sit between the two halves so the original sentence is no longer contiguous (fix: switch to a verified single-line prefix); copying a whole ghosted paragraph into the excerpt is equally invalid; do not "clean the ghosting" first and then extract — the risk of corrupting the body text outweighs the benefit.
- **Deduplication is for reading only; anchors must go back to the original block**: folding ghosting into a deduplicated version reads more comfortably, but never copy anchors from the deduplicated version — its line breaks differ from the source (the source breaks at page markers and elsewhere), so copying produces false matches that "look present but are actually not contiguous"; always assert excerpts against the **original block text** before writing.

## Append-mode multi-batch writing

- Candidates always go before the `## Per-block receipt` section; receipts **append** lines per block (old lines untouched).
- Cross-block sections (e.g. 6.13 spanning blocks 12-13): write the location as "blocks 12-13", and count receipts by **the block the excerpt came from** (matching the validator's convention, otherwise mismatch).
- Counterexample numbering runs continuously across batches — **the lead hard-codes the starting number at dispatch time** (e.g. "new entries start at 25"); sub-agents counting the previous batch's numbers themselves often get it wrong; each batch adds a `## Counterexample candidates (batch N…)` section.
- Files with structural conventions (the case track's `### Block N` section headings, etc.): the structure set in the first batch is often not reproduced by continuation batches — write "keep the file's existing structure (section headings, field format)" into the task description at dispatch time, and restore anything missing at wrap-up per the wrap-up checklist below.
- Always write back with `open(p,'w',encoding='utf-8',newline='')`: Windows text mode converts line endings to CRLF, and a single append can change the line endings of the entire stored file (an actual crash: after writing, the whole file was converted to CRLF and had to be restored from a backup). Put this line directly into every append task's description.
- **Do a "zero-change assertion" after writing back**: prove existing content is untouched with "the new file starts with the whole old file" (`new.startswith(old)`) or a word-for-word comparison of the old section — more reliable than spot-checking a few entries; when a sub-agent reports "the old N entries are untouched word for word", attach this assertion's result directly.
- **The receipt section structure of each candidate file drifts from batch to batch**: some files append a separate `## Per-block receipt (batch bN)…` section per batch, others have a single heading with per-block lines accumulated underneath — read the file's current state before appending a new batch and continue in the existing pattern; the task description should say "read the receipt section structure first, then decide how to append", not hard-code one pattern in the instruction.

## Lead wrap-up and independent verification

- A sub-agent's self-report ≠ done: spot-check artifacts while it runs, and at wrap-up run the **independent verification script** (skill step 4) on each file — parse the whole file, compare every excerpt back against its block (direct substring first, then retry after whitespace normalization to cover soft wraps), check receipt consistency, then add a **receipt block-coverage audit** (each of the five tracks covers 1..total blocks with at least one line per block; a missing number means a batch was skipped or its receipts were not written — one whole batch of the case track was lost this way after being split out for serialization, and this audit found it; **when per-block reconciliation shows a ±1 difference, first look for an explainable source**: range notations get counted once in each of two blocks, and location notes saying "block N, appears again" get parsed twice — the audit's hard criteria are: receipt lines per track = total blocks, block numbers 1..N fully covered, total receipts = entry count; a ±1 on the books is not a gap). Tracks split out for serialization (redo/deferred) must be logged in `state.md` as "pending dispatch" before dispatch and cleared at wrap-up.
- **Before the lead runs a wrap-up script a sub-agent left behind: read the whole thing and review its assertions first, and back up the target file first** — the wrap-up script is often exactly the one the sub-agent did not finish when it got truncated, and its assertion standards may carry their own bugs (always-true conditions, invented words, misused slices have all happened); with a backup in hand a crash is rollback-able, and after it runs, confirm with the independent validator.
- **The heading formats of all five tracks must match the validator's convention** (`verify_candidates.py` splits on fixed patterns; format drift makes a whole track parse as ok=0, a **false green**): framework `## N. Name` / principle `## Principle: …` / case `## Case: …` / counterexample `## Counterexample N: …` / glossary term `## Glossary term: …` (the literal examples are written into each extractor's "Record format" section). **Run the validator at every batch's wrap-up and confirm ok>0 and bad=0 for all five tracks** — "TOTAL BAD: 0" appearing alone does not count as a pass (it may mean nothing was parsed). In a measured batch 1, four tracks once had a whole track at ok=0 through freelancing (`### N.` vs `## Track name:`). **Fallback repair for batches that already drifted**: the lead uses a script to regex-replace the heading lines in that file (`re.subn`, **write back only when the replacement count = entry count**), then re-runs the validator to confirm ok>0 for that track — no need to re-run extraction. Call the validator with a native forward-slash path (`python "D:/…/verify_candidates.py" "D:/distill_xxx"`): MSYS's `/d/…` passed to native python becomes `D:\d\…` and the file is not found.
- Common loose ends and their fixes:
  - Anchor mismatch across lines → change the anchor (use the right-hand half / a whole line) and re-run;
  - Render script syntax error (unescaped quotes) → when the data cannot be fully recovered from the transcript, swap in another agent and redo it (a single task, with the whole budget);
  - Script statement order error (UnboundLocalError: variables used for EOL detection and new-section concatenation are placed before the file read) → the lead reads through in execution order, moves the statements after their dependencies, and re-runs; do not re-dispatch;
  - Newline assertion on write-back (mixed line endings in the file) → normalize to LF and write back;
  - Location written as a cross-block range "blocks X-Y" → the validator must support ranges and multi-block candidates;
  - Empty-excerpt entries (`- Source excerpt:` followed by an empty fence) → the wrap-up script counts entries with "empty excerpt"; if non-zero, fill one complete single-line sentence from the block file on the spot (discovering it only at step 4 means delaying the whole pack);
- When a sub-agent reports "the false match has been located, the correct anchor computed, only the replacement is left" or its fix script was short-circuited by a merged assertion → the lead makes the change directly: python parses and locates the false excerpt, replaces it precisely with a verified single-line anchor, and re-runs the full validation; assert each item independently in these scripts, never chain with `and` (one count=0 short-circuits all later replacements);
- Before replacing, assert `count == 1` on the replacement string; when that fails, escalate the matching scope: count > 1 means the same sentence is also quoted in other fields of the same entry ("why wrong", "related") — use a contiguous fragment of "location line + excerpt line" for a unique replacement (or include the `- Source excerpt:` field label); count == 0 means what the report says differs from what is on disk (quote/space differences) — repr the on-disk text first, then construct. When using grep to sweep for leftover `[page ` as an audit, exclude the explanatory text at the top of the file first — candidate files often open with a line like "the excerpts in this file contain no [page N] markers", which gets falsely reported as a leftover;
- Before re-running a fixed write script, add an **idempotency gate** (e.g. `assert 'Block 26: found' not in s, 'already applied?'`): once the assertion is fixed the script may be run twice, and a double run appends the whole batch's entries twice; after it runs, close out with three checks: "new numbering is contiguous + number of receipt sections + re-verification of all excerpts against their blocks".
  - Receipt numbers disagree with the validator's count → fix the receipts to the validator's "by excerpt source block" count (a sub-agent may have counted a boundary entry toward the neighboring block, which does not even match the "source location" declaration it wrote itself);
  - Candidate file section structure missing (e.g. the case track wrote no `### Block N` headings for a whole batch, and the validator attributed the whole batch to the previous block) → have the validator assign entries by the block where the excerpt actually hits in the whole corpus, and restore the headings by the hit boundaries (take the heading's page range from the block file's first and last `[page N]`);
  - Page markers left over from earlier batches (a `[page N]` embedded in an excerpt) → deleting the marker lines and upgrading the validator's normalization must happen together: normalize both sides with `re.sub(r'\[page \d+\]', '', s)`, otherwise the whole batch fails validation right after cleaning; re-run the validator immediately to confirm zero.
- Review a sub-agent script's verification assertions before using them; all four classes have stalled wrap-ups in practice: ① always-true dead code (`assert x or True`) verifies nothing; ② a check that necessarily fails on the constructed result (`assert old in new` where new is old with content spliced into the middle) always fails; ③ a state tuple that grows longer with every fix (indices shift after fields are inserted midway); ④ **invented-word assertions** — the script requires a word the "sub-agent thinks should be there" (a measured script asserted the file contained "framework name", a phrase that exists nowhere in the corpus), so the assertion never passes and the write never happens; and its summary will still cite "file grew from A to B bytes, write timestamp HH:MM" as evidence of a write — that is actually a confusion of mtime with character count, and not a single byte changed. Quick test for reviewing assertions: grep-verify that every new literal an assert references actually exists before letting it run; fix assertions with independent conditions (`startswith`/`endswith`/count receipt sections/count entries), each independent, never chained with `and`. To verify an "already written" claim: grep for the new entry numbers it claims (e.g. `^## 200\.`) and the receipt section count; 0 hits means it was not written — do not trust byte counts.
- Pitfalls in the verification script itself: `re.S` without `re.M` makes `^` match only the start of the string (once caused a whole-file false report of "missing field"); line-level comparison with "whole line equality" is too strict, use "line substring"; the five tracks have different excerpt formats + the location field has two spellings — just use this skill's own `scripts/verify_candidates.py <workspace>`, do not rewrite it.
- **The case track naturally yields little from directory-type chapters**: method lists, checklists, indexes/appendices contain only pedagogical synthetic code, with no "person—action—result"; record few or zero for the case track honestly and do not pad the count; to include synthetic examples you must first change the inclusion definition in `extractor-case.md`, and not quietly lower the bar at wrap-up.

## Measured pace

- ~4-7 minutes per batch (5 tracks in parallel); 8 batches fit in one night. Per-batch cost is manageable (flash model); the main cost is retries and wrap-up.
- When several books are queued (the user authorizes distilling several books at once), run whole books serially: finish one book's batch queue before starting the next, with no manual intervention in between; a measured night advanced 12-16 batches (the extraction stage of roughly two to three books). OCR and the cloud batch queue do not conflict when run in parallel (OCR is limited to 2 processes, see the load discipline in SKILL.md); when a book's OCR finishes that night, cut blocks and write the skeleton immediately and fill the extraction queue — do not let the pipeline idle.
