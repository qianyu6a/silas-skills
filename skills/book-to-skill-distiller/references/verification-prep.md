# Step 4 Verification · Preparation and Dispatch Recipe

Use this recipe when the raw material (frameworks + principles) runs to hundreds of items and must be merged, deduplicated, and then triple-verified. The verification standard itself (triple verification, pass-rate band) lives in Step 4 of SKILL.md; this file covers only how to operate.

## 1. Preprocessing (scripts, done by the lead)

1. **One normalized parse**: parse `cand/framework.md` and `cand/principle.md` (if stored as per-batch files such as `framework_b01..b05`, read and merge all of them) into one unified checklist: id (F001…/P001…), source, title, full item text, source excerpt, source location. Write `work/master_items.json` plus a human-readable worksheet `work/verify_worksheet.md`. **When parsing the item range, treat the line number of the first line of `## Per-block receipt` as a hard cap** — otherwise the body of the last item in the file swallows the entire receipt section into raw and carries it into the task pack; after parsing, count the items whose "excerpt is empty" (a backstop for misses in the Step 3 wrap-up), and if the count is not 0, backfill them first (pick single-line complete sentences from the block files and put them back) before continuing.
2. **Dedup pre-screen (the machine circles candidates)**: normalize "title ×2 + excerpt" into a set of character 4-grams, compute pairwise Jaccard, and mark ≥0.35 as "suspected duplicate". The framework track and the principle track often each extract the same insight once — most suspected groups are cross-track (framework↔principle) pairs; the final merge decision (whether it really is the same insight, which copy governs) is left to the verifier — the machine only circles them. Scale reference: pairwise Jaccard plus a 40-block signal scan over 777 raw items takes 1–2 seconds — just run O(n²); no inverted index or sampling optimization is needed.
3. **Cross-block evidence signal**: for the same 4-gram set, count hits against every block; if ≥3 grams hit, mark that block. **Recall is very conservative** (a reworded argument is missed outright — in practice about 40% of items get a narrow signal) — treat it as auxiliary reference only; a verifier must not eliminate an item merely because the signal is weak; check suspicious items' actual evidence with a search over the blocks/ directory as a backstop. The signal also **fails in reverse**: when the wording is generic, an item's hit blocks fill up [1..40] and there is no discrimination — in that case skip the machine-signal column entirely and locate candidates by grepping the block files for the item's core terminology; do not treat a full column of hits as evidence of "sufficient cross-chapter support".
4. **Cut task packs**: 40–55 items per pack, written to `work/parts/partN.md`. Each pack contains: full item text (first strip any `## Block X` grouping lines that got mixed in), source location, machine signal, suspected-duplicate hints. **Fold an over-small last pack (remainder <10 items) into the previous pack** — a fixed pack size cuts a stub pack of 2–3 items; after merging, every pack is still within 55 items.

## 2. Dispatch verifiers (parallel, one sub-agent per pack)

Task description template points:

- Role: distillation-pipeline verifier; background: book title, block-file directory path, total candidate count, and this pack's item-number range.
- If the pack count exceeds the concurrency cap (6 on this machine), dispatch in waves (e.g. 15 packs = 6+6+3 waves); dispatch the next wave only after the previous wave's results are collected.
- Input: `work/parts/partN.md`; output: `work/verify_result_pN.md`.
- Step 1 · Merge-dedup: for items marked "suspected duplicate", decide whether they really are the same insight; if yes → mark "merge" (state which item it merges with, which copy governs, and the merged one-sentence proposition). If the counterpart item is not in this pack, record the decision only.
- Step 2 · Triple verification: write the full three-gate standard from Step 4 of SKILL.md into the task description (the sub-agent cannot see the skill body). You must state the corroboration standard for the input type (book = "argued or applied in at least 2 different chapters").
- **Domain special case (must be written)**: if the content is knowledge this model most likely already has (typical: English grammar/usage, general programming), gate three's "smart person" must be benchmarked against "a well-educated native-speaker writer / language model", not "an ordinary person who has not read this book"; anything a standard textbook already contains is eliminated as common knowledge, while the precise conditions, exception boundaries and actionable criteria the author gives on top of public rules are kept (criterion: "can be taken directly to judge / rewrite a concrete instance"). Miss this and an entire English-usage book gets killed into an empty pack. Learning-method / self-improvement books are the same: name-level concepts such as growth mindset, flow, deliberate practice are eliminated as common knowledge as usual, but the author's personalized operational detail, concrete criteria, and the transfer increment in the cases must be kept (same criterion: can it be taken directly to judge/improve a concrete practice).
- Output format: table `| No. | Title | Decision | Gate | Reason | Note |` (Decision = keep/eliminate/merge/no-merge — "no-merge" = the two sides are complementary in granularity and both stay, counted on the keep side in statistics; Gate = verification one/two/three/merge/no-merge, write "-" for keep; Reason 1–2 sentences, must be specific); after the table a statistics paragraph: keep X / eliminate Y / merge Z / no-merge W plus 2–3 sentences of overall observation (whether there is systematic over-killing / over-passing risk).
- Hard requirements: no skipping items (self-check by listing first and last numbers and the total), write to disk every ~20 items, use the user's language for all narration; keep source quotations verbatim in their original language, and put temporary scripts under `work/`.

## 3. Aggregation

- Merge each pack's results back into the master table and execute the merges: confirmed duplicate groups collapse into one item, keeping the copy with the most complete material. **When a suspected-duplicate pair sits in two different packs, each side casts its own vote and the conclusions may contradict each other** (one side rules merge, the other no-merge, or even the opposite "which copy governs") — during aggregation, pick out every contradictory pair and arbitrate it first (the side with more complete evidence governs), and only after the ruling write the merge mapping and the keep list.
- Pass rate = (kept + no-merge) / (total − merged): merged items are removed from numerator and denominator together; "no-merge" keeps both items and counts on the pass side. A result between the normal band and the too-high line (book: 50–65%) does not trigger a re-screen — only crossing the too-high line / falling below the too-low line triggers one re-screen per the SKILL.md rules.
- Write eliminated items with their reasons into `cand/elimination-log.md`; the final checklist needs it. **The record has four sections**: round-one eliminations / re-screen eliminations (each with its gate or three-question reason) / merge destinations (an item folded into a trunk notes which item it went into — content not lost, traceable) / recoverable leads (the false kills and diluted items named in the re-screen report, each with one line on how to recover).
- **Aggregate from the table-row decisions, never from the per-pack statistics paragraphs** — in practice a pack moved "F-side absorptive merges" from keep into merge (that single pack's auto-count differed from the table rows by 5 items), and the count drift then skews the pass rate and the final keep set. Reconciliation method: parse each pack's table rows and do the four-class count as the master table; where it disagrees with the self-report, locate the specific id row and classify by the cell's original value. There is also the soft-duplicate case of "decision = keep, but the note says 'suggest merging into F0xx'" — collapse these by content when generating the final keep set (if the content already exists in the counterpart item, do not list it separately), otherwise the product carries synonymous leftovers.

## 4. Traps (actually hit in this pipeline)

- **Title format is unstable (guard for it across workspaces and batches)**: the reference implementation's regex is hard-wired to its own source book, so when switching books, look at the candidate files' actual title format before fixing the regex (e.g. in *Cookbook*, the framework track uses `## N. Title` and the principle track uses `## Principle: Title`); hierarchy and prefix can also differ between batches of the same pipeline (`## Framework N:` / `### Framework N:` / plain `## Title`). Have the parse script scan line by line and support multiple patterns; do not lock onto a single regex.
- **Use exact matching for the exclusion list**: substring filters like `'problem' in title` kill legitimate titles (e.g. "the four-way split of usage problems"). For trailing report sections (per-block receipt / verification / notes / problems / self-check …), exclude by a whole-title exact-equality list.
- **Item-count reconciliation**: after preprocessing, check that the parsed total = the sum of the per-batch receipts; a gap of 1–2 items is usually an exclusion rule hitting valid items — locate and fix it before continuing.
- **Grouping lines mixed into item bodies**: the parsed range may contain `## Block X` grouping headings; strip them before packing for the verifier.
- **Iterative tool scripts run into overwrite protection**: write_file blocks an existing file "not fully read in this task" (including a script you just wrote — re-reading may still be refused because of the paginated view). Do not re-read and retry repeatedly — incrementing the file name (v2) or rewriting in place with execute_code is the faster path; keep all scripts in `work/`.

Known-working implementations (copy them and change the paths to reuse): parse + dedup pre-screen + signal `prepare_verify2.py`, task-pack generation `generate_parts.py`, whole-batch word-for-word quote check `verify_quotes.py` — stored in `<workspace>/work/`. A second workspace (larger-scale live run) also has: `prepare_verify.py` in `<workspace>/work/` (parse + dedup + signal, with receipt cap and empty-excerpt count), `generate_parts.py` (pack cutting), `summarize_verify.py` (multi-pack aggregation + pass rate), `b7_case_verify2.py` (whole-library case attribution check). `verify_quotes.py` infers the workspace root from the script location, so a new workspace just drops it into its own `work/` to run a full re-verification. **The slim single-file-layout version** (`cand/framework.md` + `cand/principle.md`, cut directly on the two title prefixes, no INDEX.md needed): `prep_verify_art.py` in `<workspace>/work/` (parse + receipt cap + dedup pre-screen + cross-block signal + worksheet + pack cutting in one) and `summarize_verify_art.py` (multi-pack aggregation + **contradictory-pair detection** + pass rate) — for books with a single-file layout, reuse this version directly; the multi-file reference implementations' file lists and chapter tables are hard-wired to their own source books, and rewriting one to match is slower than reusing this.

## 6. Tightened re-review (resift, when the pass rate crosses the line)

When the pass rate crosses the too-high line (book >65%, transcript >45%), tighten and re-screen **one round** per the SKILL.md rules (that one round only, then pass everything straight through). Operation recipe:

1. **Build surviving units** (script): everything decided "keep" + "no-merge", plus the absorptive trunks among merges where "self governs" — identification: regex `(F\d{3}) governs` over note/reason, captured id equal to itself = trunk (survives); not equal to itself = absorbed side (dropped). Scale reference: 230 raw items → 165 units (144 keep + 19 absorptive + 2 no-merge).
2. **Tightened criteria (full text into the task description)**: three tests — **any single "yes" eliminates**: ① standard material (is it routine advice found in any general/same-genre book or standard tutorial) ② already known (would someone at the language model's own level already know it) ③ would do it naturally (would they do this without reading the book). **To survive it must satisfy at least one**: a counter-intuitive correction / b precise operational criteria (numbers, thresholds, conditions, steps) / c an actionable mechanism derived from unique experience. A same-source hint (the other version on the counterpart side) is reference only; judge once for the main item as a whole.
3. **Pack cutting**: units ÷4 rounded up, cut into 4 packs; give each unit: full item text + [same-source hint] (suspected-duplicate counterpart title + excerpt summary) + [round-one note]. Output `| No. | Title | Re-review decision | Reason | Note |` (sustain/eliminate; the reason must point to which of the three tests or which of a/b/c).
4. **Post-decision handling**: no re-check after the re-screen — pass directly; items named in the re-screen report as "source diluted by distillation / at risk of false kill" go into the "recoverable" section of the elimination log (with one line on how to recover, e.g. "the source has exact parameters such as group counts/seconds that can be restored") — this does not launch another re-screen round.
5. **Reference implementation**: `generate_resift.py` in `<workspace>/work/` (surviving-unit build + pack cutting; its `resift_result_p*.md` shows the result-table style); single-file edition for *The Art of Learning*: `prep_resift_art.py` + `summarize_resift_art.py` in `<workspace>/work/`.
