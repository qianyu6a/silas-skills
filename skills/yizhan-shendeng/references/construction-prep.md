# 第 5 步构造 · 准备与派发操作配方

通过验证的主料几百条、要归并成 6–10 个技能、每个技能一个子代理并行构造时，按本配方落地。构造标准（归并原则、数量上限、模板硬要求）在 SKILL.md 第 5 步与 `references/skill-template.md`，这里只讲怎么操作。

## 一、归并分组（脚本，组长做）

1. 从 `work/summary.json` 取最终保留集（保留＋不合并；被合并条目的内容已并入框架条，不单列）。
2. **按章自动粗分**：解析每条「原文位置」里的「第X章」；只有块号时用「章起始块表」兜底——扫每块文件开头几行找章标题，得到「起始块→章」，再 forward-fill 覆盖到每个块。实战分组参考（约 10 组）：数据处理与文本 / 迭代与生成器 / 文件IO与编码 / 函数与装饰器 / 类与元编程 / 模块与导入 / 网络与IPC / 并发 / 脚本调试与性能 / C扩展与跨语言。
3. **人工校正边界**：自动分组按章走，但"用户会在同一场景下需要它们"才是真的分组标准——把错位主题挪组（实例：装饰器小节落在第九章，应归「函数与装饰器」组而不是「类与元编程」组）。校正后组内不空转。
4. 每组落盘 `work/groups/<组名>.md`（条目全文，格式同验证任务包）。

## 二、素材切分（脚本）

- 案例素材：`候选/案例.md` 按「### 第 N 块」分段切，按块号归组 → `work/groups/cases_<组>.md`。
- 反例素材：`候选/反例.md` 每条带「- 原文位置：第 N 块」字段，按该块号归组 → `work/groups/counter_<组>.md`。
- 各候选文件的条目标题格式各不相同（框架 `## N. `、原则 `## 原则：`、案例 `## 案例：`、反例 `## 反例 NNN：`）——每个文件写自己的解析正则，别指望一个正则套四个文件。

## 三、派发构造员（并行，每技能一个子 Agent）

任务描述要点：

- 角色：技能包构造员；背景：书名、主料已过三重验证、本组覆盖主题。
- 输入五件全给路径：①本组主料 `groups/<组>.md`；②案例素材（说明文件较大 ~40–90KB，用 grep 定位、不必全读）；③反例素材（同上）；④`skeleton.md`（必读「盲点与边界」节——「什么时候不该用它」的唯一来源）；⑤`references/skill-template.md`（必读全文）。
- 格式硬要求照抄进任务：首行 `---`；只写 name+description；description 60–120 全字符数（先写场景句再数字数）；六段结构；「怎么做」5–12 条可执行动作；自检「遮住出处重读，像章节摘要就重写」。
- 预算约 10–15 次工具调用一次成型（读模板/骨架→读主料→grep 素材→写盘→探针自检）；临时脚本放 `work/` 且带组名前缀（同批共用 work/，同名会互撞）。
- 写盘一次完成，或先整读再覆盖——宿主有防覆盖保护，分批追加同一文件会被拒。
- 格式样板除 `skill-template.md` 外，再给一份**已完工的同类 SKILL.md 的路径**（上一本结构相同的包；同书后续波次用这本书第一个完工的包）——照抄现成结构比抽象模板直观，跨包风格也更齐。
- 素材大小按**字符数**估算（python `len()`），别按 `wc -c` 的字节数：中文本里字节数约为字符数的 2–3 倍（按字节显示 183KB 的组素材，实际约 76K 字符，子代理单次就能读完）——「超 60K 字符才用 python 分段读」，不要为字节数虚高去拆文件。
- 质量要求写进任务并建议自检：每条保留条目至少被「怎么做」或「判断标准」吸收（可合并同类）、不得编造；交付前用**关键词探针**自查一遍（每条保留条目选一个特征词，检查它出现在正文）——构造员会据此主动补上几处漏吸收。探针报缺失先复核假阳性：关键词写法与正文措辞不同会误报，「改写而非遗漏」＝吸收成功。

## 四、收尾（组长做）

- 全部返回后跑**元信息闸门脚本**逐项复验：首行 `---`／name=文件夹名／小写连字符／description 按 `len()` 全字符数 60–120／无多余字段／`技能包/` 根目录只有技能文件夹。**不采信子代理自报**——它们会自写校验脚本并报 PASS，独立复验照跑。
- **组标签与素材内容对不上时，以素材为准。** 计划分组常按预期的章号映射写成，实际块内容可能与标签整体错位（实例：三组构造员同时上报「标签与内容不符」、错位一格）。处理：①构造员按素材实际内容写，不按错标签硬写、也不为凑标签另取素材；②组长按实际内容给成品改名——`mv` 文件夹的同时改 SKILL.md 里的 `name:` 字段（**两处都改**，改完 grep 复验），改名与原因记进 `状态.md` 和最终 `清单.md`；③构造员主动报告错位是有效信号，不算失败。
- **进盲测前交叉扫一遍兄弟技能的 description 触发词。** 两个技能都宣称同一触发概念（如「变量命名」同时出现在两个包里）时，盲测大概率判「边界」——可接受（触发哪个都能帮上），但要预判到；想更干净就把更贴的保留、另一个改成差异化触发词——**在盲测之前改**，盲测后不再动 description。
- 抽查 1–2 份 SKILL.md 正文（遮住出处重读一遍），质量不合格的返工；全部合格再进第 6 步盲测。
- 参考实现：预处理 `prepare_verify.py`、切包 `generate_parts.py`、汇总 `summarize_verify.py` 在 `<大书工作区>/work/`（分组脚本按本配方现写即可）。
